# UNOFFICIAL Tails container (adapted from a Tails 7.16 ISO root filesystem) for Kasm  - v0.11

**This is not Tails.** It is the Tails 7.16 root filesystem (extracted from an ISO the owner holds) run as an unprivileged Docker container under KasmVNC.
Not provided: the Tails kernel, memory wipe on shutdown, MAC anonymisation, Tails' own firewall/netns/onion-grater/AppArmor policy set, Wayland (X11 under KasmVNC instead). A container shares the host kernel. No claim of Tails support, certification or security equivalence; "accepted" below means the listed tests passed on this installation.
The Tails new-tab page still says "You are running Tails 7.16" because it is Tails' own page; it is not true of this container.

## Image chain (every build is a new immutable tag; never retag under running containers)
`0.3` (imported rootfs + first prototype) -> `0.4` (Tor gateway front end, control proxy) -> `0.8` (0.5 relay + lock + bwrap shim v2, 0.6 profile banner + usb-protection off, 0.7 profile/lock-notice fixes, 0.8 control-client fix) -> **`0.11`** (cumulative `Dockerfile` here is `FROM 0.4` and contains every later step): 0.9 launcher argument fix, control-protocol framing fix and session-preserving control forwarder; 0.10 private profile home; 0.11 explicit launcher argument parser. Rollback: tag `0.8` (kept) plus the previous workspace definition.

## Architecture (all pieces are Tails-only; nothing is shared with the stock Tor-Browser workspace)
- **Gateway `kbtails-tor-gw`** (own Tor process, own DataDirectory/cookie, own bridges, networks `kbtails_int` internal + `kbtails_eg`). The stock Tor-Browser workspace runs its own Tor inside its own container; stopping/restarting it does not touch Tails (tested). `gateway/kbgw.py` is the only thing desktops can reach: SOCKS front ends with a destination policy (non-global, internal names, the owner's domain and WAN aliases refused before Tor is asked), per-desktop circuit isolation (SOCKS user `kbc-<desktopIP>-<epoch>-<hash>`), and a **filtered control port 9051** (null auth to the desktop, SAFECOOKIE to Tor; own circuits/streams only; `NEWNYM` = this desktop's epoch + closing only its circuits; no SETCONF/raw access). Verified: the gateway's raw circuit list grouped by SOCKS user equals each desktop's filtered view exactly.
- **Callback relay `kbtails-kasm-relay`** (`relay/`): the Kasm session scripts POST `/api/kasm_session_log` (and `/api/set_kasm_session_status` in the profile-sync/size-limit paths) to the Kasm API. Two things broke that silently: Tails' `/usr/local/bin/curl` wrapper forces every curl through Tor (which refuses the internal name), and the peer-isolation table blocks desktop -> `kasm_proxy`. v0.5+ points the three Kasm scripts at the relay over `/usr/bin/curl`. The relay accepts only those two POST endpoints (token-only query, JSON, <=64 KB, 60 req/min/source), forwards to `https://proxy:443` (Kasm validates the session JWT) and is not a generic proxy. Desktops still cannot reach `kasm_proxy` itself.
- **Peer isolation `host/kbtails-isolation`**: nftables bridge-family table; allows replies, desktop -> gateway and relay, `kasm_proxy` -> desktops (streaming); everything else inside `kbtails_int` is dropped.
- **Self-healing `host/kbtails-ensure`** (systemd service + 5-minute timer; Docker `restart=unless-stopped` on the containers): recreates/starts a missing or stopped gateway/relay and re-applies the isolation table. Tested: removed relay + stopped gateway -> both back in seconds; killed Tor -> fail-closed, back in ~16 s with no bridge selection.
- **Docker runtime `kb-tails`** (`host/kb-runc`, registered in `/etc/docker/daemon.json`): the Docker Engine API has `HostConfig.MaskedPaths/ReadonlyPaths`, but Kasm's docker-py 7.1.0 cannot send them (tested in a Kasm-managed launch: `TypeError: run() got an unexpected keyword argument 'masked_paths'`; `systempaths=unconfined` is rejected by the daemon API). Docker's supported extension point for editing the OCI spec is a runtime wrapper (same pattern as nvidia-container-runtime). `kb-runc` empties `maskedPaths`/`readonlyPaths` **only** for containers that select runtime `kb-tails` and **refuses to start** them unless: AppArmor `kb-tails`, `noNewPrivileges`, a seccomp filter, a non-root user, no `CAP_SYS_ADMIN`, and the env marker `KB_TAILS_RUNTIME=1` are all present. Compensating control: AppArmor `kb-tails` denies every formerly masked/read-only path (verified at runtime: `/proc/kcore`, `timer_list`, `sched_debug`, `keys`, `latency_stats`, `kmsg`, `/proc/acpi`, `/proc/scsi`, `/sys/firmware`, `/sys/kernel/security`, sysctl writes, `mount`). This restores the browser sandbox's own PID namespace + fresh procfs and `--disable-userns`.
- **Hardening of the container** (Kasm run_config): not privileged, no host network/PID, no Docker socket, no devices, no added capabilities, `no-new-privileges`, custom seccomp (Docker default + the namespace syscalls bubblewrap needs, **minus `ptrace`/`process_vm_*`/`kcmp`**), AppArmor `kb-tails`.
- **Tails' own Tor Browser** (Flatpak `org.boum.tails.TorBrowser` under bubblewrap, **unmodified bubblewrap arguments**; `kb-bwrap` now only verifies `/proc` is unmasked and fails closed otherwise). Runtime-verified inside the sandbox (`kb-sbx-test`): own user, mount **and PID** namespace, no capabilities (CapBnd 0), `NoNewPrivs`, two seccomp filters, AppArmor `kb-tails`, `unshare` blocked, `ptrace` EPERM, `/data` and `/share` invisible, 5 visible PIDs (its own), direct network blocked.
- **Truthful Tails UI**: `kb-torstatus` keeps `/run/tor-has-bootstrapped/done` only while the gateway reports bootstrap 100 % and a circuit; `kb-onioncircuits` runs Tails' circuit viewer on the filtered control port (own circuits only); `kb-tca` shows the true gateway state in place of the systemd-based Tor Connection Assistant. Verified in real Kasm sessions with two real v3 onion services (torproject and DuckDuckGo onions, both obtained from the services' own headers): rendered pages, `HS_CLIENT_REND` circuits and onion streams in this session's view only.
- **Screen lock** (`kb-lock`, behind Tails' own "Lock Screen" menu entry `tails-screen-locker`): GNOME's lock needs GDM + PAM which a container lacks. `kb-lock` asks for a passphrase chosen at lock time (scrypt hash in memory only), covers the screen with a keyboard/pointer-grabbing window, delays failed attempts (2^n s, max 30 s). Tested: lock, bypass keys, wrong passphrase, unlock. It complements - not replaces - Kasm's authenticated access: a session URL without a valid Kasm login returns 401 and Kasm's idle disconnect / login lifetime force re-authentication on resume. (An X11 grab-based locker is not equivalent to a PAM/GDM lock; the container's only X clients are the user's own.)
- **Persistence (optional, explicit)**: ONE tile. It has Kasm 1.19 Persistent Profile at `/mnt/kasm_profiles/{user_id}/{image_id}` (unique per user and per workspace). The launcher offers **Enabled / Disabled / Reset**: Disabled = disposable (the saved profile is neither read nor written), Enabled = restore/keep the private saved profile, Reset = clear this user's saved profile for this workspace. Kasm lists Enabled first and cannot change that default, so the choice is deliberate and the session shows a notification of the active mode (`/tmp/kb-profile-mode`). A saved profile is a plain directory on the Kasm host: **not encrypted at rest and not Tails' encrypted Persistent Storage**. Kasm refuses a second concurrent session on the same profile; an in-container `flock` is a second guard. The group `Tails test (restricted)` sets `allow_persistent_profile = True`; webcam, microphone, printing, downloads and uploads stay denied.

## Fixed in 0.9-0.11 (owner-observed defects, root causes)
- **Tabs `file:///usr/local/lib/tor-browser/@@u` and `https://u/`**: Tails' menu entry runs `tor-browser @@u %u @@` (Flatpak file-forwarding syntax). Tails' own launcher passes it to `flatpak run --file-forwarding`, which consumes the delimiters; the container's launcher shim (`kb-tor-browser`) replaced that launcher without the flag, so `@@u` and `@@` reached Firefox as URLs. The shim now parses its arguments: delimiters and field codes are dropped, options are refused (as in Tails), URLs are passed as plain arguments, anything else goes through `--file-forwarding`. Tested: no URL, one URL with query characters, several URLs, `xdg-open` from the desktop; no literal `@@`/`@@u`/`%u` ever reaches Firefox.
- **"Onion Circuits is not responding"**: the filtered control port re-framed multi-line data replies (`GETINFO ns/id/<fp>`, sent when a circuit is selected) without the terminating `.` line, so stem in Onion Circuits' GTK main thread waited forever. Reproduced against the live gateway (reply ended `...250 OK` with no `.`), fixed in `gateway/kbgw.py` (terminator kept; per-command timeouts return a 551 instead of hanging; relay-descriptor lookups cached).
- **Browser "can't communicate with the external Tor" banner after a gateway restart**: `fwd.py` now relays the control port as a protocol-aware, session-preserving proxy: it keeps the browser's connection open, reconnects upstream, replays the null authentication and the last accepted `SETEVENTS`, answers in-flight/arriving commands with a prompt `551` while the gateway is away, reports the circuits/streams the client had seen as closed (they are), and never fabricates other state. After a gateway stop/start the browser and Onion Circuits recover without any click (browser traffic itself resumes when Tor re-bootstraps, ~15-40 s).
- **Saved-profile directory**: Kasm creates the profile leaf directory mode 0777; the session now sets its home to 0700 at start (the host parent `/mnt/kasm_profiles` is root-only 0700, so the 0777 was never reachable by other host users, but there was no reason to leave it).

## Remaining boundary (not equivalent to booted Tails; stated, not hidden)
- Shared host kernel (kernel exploits, host-wide resources), no memory wipe, no MAC anonymisation, X11 instead of Wayland, no Tails firewall/netns design; Tor-only egress is enforced by the separate gateway and Docker networking instead.
- The browser sandbox shares the container's network namespace (intended: the container network is the isolation) and IPC namespace (X11 needs it).
- `/data` and `/share` are mounted into every Kasm workspace by the All Users group setting `volume_mapping`; they exist in this container but AppArmor denies all access and they are invisible inside the browser sandbox. Removing them would change every workspace.
- Reaching `kasm_proxy` is allowed only for the relay's two callback endpoints (through the relay), never directly.
- The kb-runc wrapper must be kept in step with Docker/runc upgrades (it only edits two spec arrays and re-execs `/usr/bin/runc`).
- NEWNYM is per desktop (gateway-side epoch), not Tails' global signal.
- The in-container lock is a grab-based locker, not PAM.

## Install (local image: preload required, not downloadable)
1. On the Kasm agent host: build the image from your own Tails rootfs (`Dockerfile` builds on the imported rootfs image `...:0.4`) and tag it `ghcr.io/daledibbadel/tails-unofficial:0.11`. Stage `gateway/*`, `relay/*`, `host/*` (create `gateway/deny.conf` from the example: your own public host names and WAN address; the repository file is a placeholder) (see `host/kbtails-ensure.sh`: files under `/opt/kbtails`), load `profiles/kb-tails.apparmor` with `apparmor_parser -r`, install `host/kb-runc` as `/usr/local/sbin/kb-runc` and register it as runtime `kb-tails` in `/etc/docker/daemon.json` (`systemctl reload docker`), install `host/kbtails-isolation.sh` and `host/kbtails-ensure.*`, enable the timer.
2. Add the registry workspace with Docker Registry left blank (local image); the image is protected from Kasm's pruner by the workspace reference and the running gateway/relay containers. `tools/kasm_tails_install.py update|disposable` (admin API) applies the exact run_config, persistent path and the disposable tile.
